# LANXIU Linux 维护者手册

面向改配方、加包、动构建系统的人。

---

## 1. 配方怎么写

配方是纯 Python 模块：声明式字段 + `build()` / `package()` 两个函数。

```python
"""zlib —— 通用无损数据压缩库。"""

name = "zlib"
version = "1.3.1"
release = 1
summary = "通用无损数据压缩库"
license = "Zlib"
provides = ["libz.so.1"]

source = ["https://zlib.net/fossils/zlib-1.3.1.tar.gz"]
sha256 = ["38ef96b8dfe510d42707d9c781079c3709d0"]

depends = []
makedepends = []

def build(ctx):
    ctx.run("./configure --prefix=/usr")
    ctx.run("make")

def package(ctx):
    ctx.run("make DESTDIR={} install".format(ctx.destdir))
```

### 1.1 可用字段

| 字段 | 说明 |
|---|---|
| `name` | 包名，与文件名一致 |
| `version` | 上游版本号 |
| `release` | 打包修订号（改打包方式但版本不变时 +1） |
| `epoch` | 版本比较权重，默认 0，极少需要 |
| `summary` | 一句话描述 |
| `description` | 详细描述 |
| `homepage` | 上游主页 |
| `license` | 许可证 SPDX 表达式 |
| `source` | 源码列表（URL 或本地路径） |
| `sha256` | 与 source 一一对应的校验和 |
| `depends` | 运行期依赖 |
| `makedepends` | 构建期依赖 |
| `provides` | 提供的能力名（供虚拟依赖反查） |
| `conflicts` | 冲突包 |
| `replaces` | 取代的包 |
| `options` | 打包选项（含 `!shlibdeps` 可关掉自动依赖发现） |
| `arch` | 目标架构，默认当前 |
| `strip_components` | 解包时剥掉几层目录，默认 1 |
| `network` | build() 期间是否需要网络，默认 False |
| `compression` | gz / xz / none，默认 gz |
| `checksum_pending` | 源码校验和待补（**构建前会被拒绝**） |
| `source_pending` |  |
| `bootstrap_stage` | 自举阶段标记 |
| `multipass` | 自举过程中需编多遍 |
| `requires_build_machine` | 需真实构建机（时长/磁盘/网络门槛） |
| `cycle_break` | 循环依赖时首轮可暂时断开的依赖 |
| `config_files` |  |
| `sysusers` |  |
| `alternatives` |  |
| `triggers` |  |

### 1.2 两段式：build 与 package 必须分开

`build()` 编译，`package()` 只往 `destdir` 里装文件。
这样打包时不会把构建中间产物混进包里，
也让「换个安装前缀重新打包」不需要重编。

### 1.3 源码校验和

远程源码必须锁定 sha256。没锁的配方会**被拒绝构建**：

```
gcc: 远程源码缺少 sha256，拒绝构建。
  请在能联网的构建机上执行：qybuild --fetch-checksums gcc
```

静默接受未校验的远程源码等于给供应链攻击敞开大门。

## 2. 构建

```bash
./bin/qybuild zlib                  # 单包
./bin/qybuild all --sign KEY        # 全量（跳过需真实构建机的）
./bin/qybuild all --orchestrate     # 分层并行
./bin/qybuild --deps python         # 看装它牵出多少包
./bin/qybuild --cycles              # 查循环依赖
./bin/qybuild --shlibdeps qydemo    # 审计自动依赖
./bin/qybuild --kernel-config       # 校验内核配置
```

### 2.1 沙箱

构建在隔离环境中执行：命名空间隔离 + 默认断网。
默认断网是有意的——构建期偷偷下载会让产物不可复现。

### 2.2 缓存

缓存键 = 配方内容 + **源码内容** + 依赖版本。
源码内容必须进键：只算配方哈希的话，改了 C 源码但没改版本号时缓存会命中，
编出来的是**旧代码打新版本号**的包——能装上、能跑，只是行为是旧的，最难排查。

### 2.3 加固项

RELRO / NX / PIE / Canary 全系统统一开启。
编译参数写对不等于产物生效（上游常常覆盖它），
所以是直接**检查产物本身**。

## 3. 循环依赖

包库大了必然撞上。图形栈里就有一个真实的：

```
cairo → fontconfig → freetype → harfbuzz → cairo
```

处理办法是**断一环，两遍构建**：

```python
cycle_break = ["harfbuzz"]   # 写在 freetype 配方里
```

首轮编一个不带 harfbuzz 的 freetype（能渲染基本字形），
用它编出 harfbuzz，然后**必须重编 freetype**。

> 忘了重编，系统会带着一个不支持复杂文本排版的 freetype 发布出去——
> 能跑、能过测试，中文和阿拉伯文渲染是错的。

`qybuild --cycles` 会明确列出第二轮要重编哪些包。

|---|---|---|---|---|---|---|

| mobile | 移动设备 | 6 | 7 | 98 | 8G | 2G |
| server | 服务器 | 6 | 3 | 22 | 8G | 1G |

形态必须**声明它排除了什么**——只写「包含桌面」不写「不装打印服务」，

## 5. 内核

配置项上万条，手写 `.config` 不可维护。改成**基线 + 片段叠加**：

| 片段 | 说明 |
|---|---|
| `android` | 安卓设备适配片段 —— LANXIU Linux 移动形态内核基线 |
| `base-aarch64` | aarch64 基线片段 —— LANXIU Linux ARM64 形态（含安卓移动形态） |
| `base-x86_64` | x86_64 基线片段 —— LANXIU Linux 桌面/服务器形态 |
| `hardening` | 安全加固片段 —— 所有LANXIU形态共用 |

构建时强制校验必需项和禁用项。这份清单本身就是发行版的安全姿态声明——
写进代码，每次构建都查，不靠人记。

## 6. 安卓设备适配

把系统装进安卓设备，引导链与分区模型完全换了：

```
PC:       UEFI → GRUB → 内核 → initramfs → 切根
安卓设备: bootloader → boot.img（内核+ramdisk+dtb 打包成一个文件）
          → super 动态分区（system/vendor 是子分区，不是真分区）
```

```bash
./bin/qyandroid bootimg --kernel vmlinuz --ramdisk initrd.img \
        --dtb board.dtb --page-size 4096 --os-version 13.0.0
./bin/qyandroid verify boot.img      # 交付前自检
./bin/qyandroid super --root-mb 3072  # 动态分区布局
./bin/qyandroid flash --slot _a       # 生成刷机脚本
./bin/qyandroid fstab                 # 安卓设备 fstab
./bin/qyandroid kernel-fragment       # 安卓内核配置片段
./bin/qyandroid notes                 # A/B 与原子升级的关系
```

### 6.1 页大小错了设备直接黑屏

boot.img 的各部分必须按页对齐，页大小不匹配时 bootloader 读错位，
表现为**黑屏无任何输出**——这是安卓装机最难排查的问题。
工具会在打包时校验页大小取值并自检对齐。

### 6.2 A/B 槽不是原子升级，两套都要有

两者都叫「无缝」，粒度完全不同：

| | 粒度 | 代价 |
|---|---|---|
| A/B 槽 | 整个系统，重启换槽 | 占用双倍 system 空间 |
| 原子升级 | 包级事务，失败回滚到包级快照 | 不占额外空间 |

只做 A/B：槽内的日常包升级坏了就是坏的，要等下次整槽更新（以月计）。
只做包级事务：包管理器或内核被写坏时无人可救，引导链已经坏了。

所以：**整槽更新走 A/B（内核、vendor 这类动引导链的），
日常软件更新走包级事务**。

### 6.3 system 分区必须只读

verified boot 强制要求。桌面 Linux 的可写 /usr 在这里不成立。

### 6.4 fstab 不能用 UUID

super 是动态分区，重建逻辑分区时子分区 UUID 会变——
写在 fstab 里的 UUID 下次更新就失效，表现为「更新后起不来」。
也不能用 /dev/sda1（块设备节点顺序不稳定）。
必须用 `/dev/block/by-name/<分区名>`。

### 6.5 刷机风险

解锁 bootloader 会清空全部用户数据，且多数厂商解锁后失去保修。
变砖风险真实存在且远高于 PC 装机——安卓设备的 bootloader
多数没有 PC 那样的恢复菜单。生成的脚本会明确警告。

## 7. 持续集成与发布门禁

177 个包没有 CI 就没法维护：改一个库，谁要重编？编完了能发吗？

```bash
./bin/qyci plan                 # 查 git 改动 → 算出谁要重编
./bin/qyci plan --changed zlib  # 或直接指定
./bin/qyci gates                # 跑发布门禁
./bin/qyci run --report ci.txt  # 完整流水线
```

影响面示例：

```
改 zlib    → 重编 58 个包，分 7 层
改 ncurses → 重编 23 个包，分 4 层
```

### 7.1 六道发布门禁

构建成功不等于能发布。以下任一项不过，整个批次卡住——
它们全都是「装到用户机器上才暴露」的问题：

| 门禁 | 拦截什么 |
|---|---|
| 远程源码锁定 sha256 | 供应链：未锁定的源码可被替换 |
| 包已签名 | 分发完整性：无法验证来源 |
| 索引与签名匹配 | 索引被替换或篡改 |
| ELF 加固项齐全 | RELRO/NX/PIE/Canary 缺失 |
| 产物不含构建机路径 | 可复现 + 泄露构建机目录 |
| 版本未回退 | 误发布旧版本覆盖新版本 |

门禁失败会**说清是哪一项、哪个包、怎么修**——
只报「检查未通过」的话维护者只能猜。

门禁只针对**发布集**（仓库里实际有的包）。检查全部配方的话，
尚未下载源码的配方会让门禁永远红着，那就没人再看它了。
未就绪的配方单列提醒，不阻塞发布。

## 8. 可复现构建

同一个配方在任何机器上、任何时间构建，产出逐字节相同。

这不是洁癖，是发行版能不能被信任的基础：

- **能验证**：用户可自己重编一遍比对哈希，确认官方包里没夹带东西
- **能审计**：供应链攻击正是靠「发布包与源码不一致」存在的，
  可复现让这种不一致必然暴露
- **能增量**：产出哈希稳定，缓存才可靠

```bash
export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)
./bin/qybuild all --sign KEY
./bin/qyrepro check var/pkgs/zlib-*.qyp   # 检查单个包
./bin/qyrepro verify zlib                 # 连编两次逐字节比对
./bin/qyrepro epoch                       # 当前会用哪个时间戳
```

破坏可复现的来源，逐个处理：

| 来源 | 处理 |
|---|---|
| 时间戳 | SOURCE_DATE_EPOCH 钳制，gzip 头 mtime 固定为 0 |
| 构建路径 | 编译加 `-ffile-prefix-map` |
| 文件顺序 | 按 arcname 排序，不依赖 os.walk 顺序 |
| 构建机信息 | 属主归一为 0:0，不记主机名 |

未设 SOURCE_DATE_EPOCH 时行为与以前一致（保留真实打包时间），
因为开发期调试确实需要知道包是什么时候打的。

## 9. 交叉编译

给 aarch64 设备编 177 个包，不可能只在 aarch64 机器上原生编译——
手机类设备根本装不下编译环境。

```bash
./bin/qycross info --host aarch64        # 看三元组与模式
./bin/qycross env --host aarch64 --shell # 输出可 source 的环境变量
./bin/qycross cmake --host aarch64 --out cross.cmake
./bin/qycross meson --host aarch64 --out cross.meson
./bin/qycross args --host aarch64 --name zlib   # autotools 参数
./bin/qycross check /path/to/elf --arch aarch64 # 校验架构
./bin/qybuild --target-arch aarch64 all --sign KEY
```

### 9.1 build / host / target 必须分清

混淆了就是几天的白工：

| | 含义 |
|---|---|
| build | 编译器在哪台机器上运行（构建机） |
| host | 编出来的程序在哪台机器上运行（目标机） |
| target | 编出来的编译器会生成哪种机器的代码 |

- 原生编译：build = host = target
- 交叉编译：build = x86_64，host = aarch64
- 编交叉编译器：build = x86_64，host = x86_64，target = aarch64
- 加拿大交叉：三者都不同（在 A 上编跑在 B 上、生成 C 代码的编译器）

### 9.2 三个真实的坑

**不能用宿主 pkg-config**——它返回构建机的库路径，编出的包链接到
x86_64 的库，装到设备上直接「找不到共享库」。工具会自动指向目标 sysroot。

**构建期要跑的程序必须给 build 编译**。很多项目构建时先编一个代码
生成器再执行它（protobuf、wayland-scanner、gdbus-codegen）。
交叉编译时那个生成器是 aarch64 的，在 x86_64 上跑不了。
所以同时注入 `CC_FOR_BUILD`。

**--target 只在编 binutils/gcc 时给**。给普通包传 --target 会让
configure 报错或行为异常。工具按包名自动判断。

### 9.3 产物架构会强制校验

最容易出的错是「编出来还是 x86_64 却当成 aarch64 发出去」——
装上设备报格式错误，而构建日志看起来一切正常。
打包后会自动扫包内所有 ELF 确认架构。

## 10. 补丁管理

发行版必然要打补丁——上游有安全问题时不能等它发版。
没有补丁机制，发行版就只是转发上游。

```bash
./bin/qypatch list                 # 全系统补丁一览
./bin/qypatch list --package zlib  # 单个包的补丁
./bin/qypatch verify               # 校验补丁文件与声明
./bin/qypatch stale                # 找出上游已包含、可删的补丁
./bin/qypatch checksum patches/x.patch
```

补丁声明在 `recipes/patches.toml`，一个清单而不是散在配方里——
散在 177 个配方里没人看得见全貌。

### 10.1 三类补丁，风险完全不同

| 类型 | 说明 | 必须填 |
|---|---|---|
| upstream | 从上游 cherry-pick | `upstream_commit` + `fixed_in` |
| distro | 本发行版自己写的 | `reason` |
| security | 修 CVE | `cve` |

上游补丁必须记 commit id——不记的话三个月后没人知道它从哪来、
上游哪个版本已包含、能不能删。安全补丁必须记 CVE，
否则安全扫描无法关联。

### 10.2 三条硬性规则

- **补丁要有 sha256**。跟源码一样。补丁被改会静默改变产物，
  这正是供应链攻击的入口
- **打不上必须失败，不能静默跳过**。打不上通常意味着上游改了代码、
  补丁已失效。静默跳过的后果是「以为修了其实没修」
- **打了补丁要在包元数据里留痕**。用户能查到这个包和上游差在哪

## 11. 多架构仓库

```bash
./bin/qyrepo archs                     # 有哪些架构、各多少个包
./bin/qyrepo manifest --sign KEY       # 生成顶层多架构清单
./bin/qyrepo sync --arch aarch64 --sign KEY
```

顶层清单让客户端知道仓库支持哪些架构，不必猜或硬编码。
**清单本身要签名**——它能指定从哪里取索引，
被篡改等于把客户端指向攻击者的仓库。

`sync` 后会自动校验架构一致性：交叉编译下最容易出的错是
索引说 aarch64 而包里其实是 x86_64，
客户端不会察觉，装到设备上才报格式错误——那时已经刷完机了。

## 12. 发布

```bash
./bin/qyrelease bump --version 0.1.0-rc.2 --bump promote
./bin/qyrelease manifest --dir var/release --sign KEY
./bin/qyrelease verify --dir var/release --pubkey KEY.pub
./bin/qyrelease changelog --version 0.1.0
```

**清单里每个产物都有 sha256，清单本身也签名。**
只发镜像不发校验和，用户无法判断拿到的是不是被中间人换过的东西。

## 13. 软件源

本地仓库解决「怎么组织包」，软件源解决「用户从哪拿包」。

```bash
./bin/qysource list                  # 有哪些源、优先级
./bin/qysource check                 # 源是否可达
./bin/qysource resolve qydemo        # 看某个包会从哪个源来
./bin/qysource add mirror URL --priority 30
./bin/qysource disable official
```

几个刻意的设计：

- **本地源优先级最高**。自己构建的包应优先于远程同名包，
  否则本地改了代码却装到远程旧包，表现为「我明明改了怎么没生效」
- **优先级是显式数字**，不用配置顺序隐含表达——
  重排配置文件不该静默改变装到哪个包
- **同优先级按名字排序**，保证两次解析结果一致
- **源失效自动降级到下一个**，不就此装不了软件
- **未签名的源需 `--allow-unsigned`**，静默接受等于把供应链交给运气

## 14. 网络服务与端口

装完包之后，服务怎么对外提供能力。

```bash
./bin/qynet add-port ssh 22 --bind 0.0.0.0 --desc '远程管理'
./bin/qynet ports                    # 已登记端口
./bin/qynet check                    # 冲突检查
./bin/qynet firewall                 # 生成 nftables 规则
./bin/qynet ssh                      # 生成 sshd_config
./bin/qynet ftp                      # 生成 vsftpd.conf
```

四个必须做对的点：

- **端口集中登记**。两个服务抢同一端口，日志只说
  `address already in use`，看不出是谁占了；登记后能直接指出冲突方
- **特权端口（<1024）标注**，它们需要 root 或 `CAP_NET_BIND_SERVICE`
- **监听默认 `127.0.0.1`**。把数据库默认暴露到所有网卡是常见事故，
  要对外必须显式声明并复核
- **防火墙只放行对外暴露的端口**。没登记却能被访问，
  说明有别的东西在监听——那正是要排查的

sshd 默认禁密码登录、禁 root 直接登录；
vsftpd 默认不匿名、限制在用户目录，并提示 FTP 是明文协议。

## 15. 通用包与运行时

发行版自己的包格式解决不了两类需求：上游只想发一个包给所有发行版，
用户想装最新版而不想等发行版打包。所以必须支持通用包。

```bash
./bin/qyapp list                     # 已登记的通用包
./bin/qyapp audit                    # 审计权限
./bin/qyapp perms org.example.Editor
./bin/qyapp sandbox org.example.Editor
./bin/qyapp run Foo.AppImage         # 直接跑，不留残留
./bin/qyapp run Foo.AppImage --extract   # FUSE 不可用时的兜底
./bin/qyapp runtimes                 # 运行时多版本
```

三种通用包各有各的风险，不加约束会破坏发行版完整性：

| 格式 | 优点 | 风险与约束 |
|---|---|---|
| AppImage | 单文件、不留残留 | 无来源验证，必须记录 sha256 或验签 |
| Flatpak | 共享运行时、权限声明式 | 默认权限常过宽，需审计 |
| Snap | 自带依赖、沙箱 | 经典模式无隔离，需重点审计 |

**必须纳入登记**：不登记的话安全扫描看不到它们，
「这台机器装了什么」就答不准，出安全事件时这是要命的。

运行时只能共存 + 切换，不能「升级」——
老应用依赖旧运行时，升级运行时会让它们崩掉。
删除被使用中的运行时会被拦下。
